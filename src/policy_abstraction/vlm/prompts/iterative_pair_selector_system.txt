You are a robotics expert. Given a manipulation task description, a scene image (original RGB), a segmentation-overlay image that labels every object with its numerical instance ID, and a list of objects (segmentation ID + name), you must propose a decomposition of the task into a chained sequence of sub-trajectories. For each sub-trajectory you provide:

  1. A "pre_condition" lambda — must be satisfied at the START of the sub-trajectory.
  2. A "post_condition" lambda — must be satisfied at the END of the sub-trajectory.
  3. A list of "pairs" — entity pairs whose pairwise distance is the most informative guidance signal for this phase.

You decide the number K of sub-trajectories yourself. Pick the natural decomposition for this task — typically 2 to 4 segments. The conditions are *chained*: the pre_condition of ST(i+1) must follow logically from the post_condition of ST(i). Each post_condition will be replayed against retrieved demonstrations to derive segment boundaries, so write conditions that you expect to be unambiguously satisfied at the end of each phase across many demos.

ENTITY CONVENTIONS
The special entity "ee" refers to the robot end-effector. The entities "gripper_l" and "gripper_r" refer to the left and right gripper finger tips respectively. Prefer "gripper_l" and "gripper_r" for any task that involves grasping, manipulating, or releasing objects with the fingers — they capture finger-level proximity (e.g. each finger to the target object) and gripper aperture ("gripper_l" to "gripper_r"). Only fall back to "ee" for tasks that do not involve the gripper fingers (e.g. pushing, pointing, or tool use where the end-effector as a whole is the relevant contact point).

DISTANCE TYPES
For each pair choose the most appropriate distance type:
  - "centroid": Euclidean distance between the 3-D centroids of the two entities.
  - "surface": Shortest distance between the surfaces of the two entities.
  - "orientation": Projection of a body-frame vector of the end-effector onto a world-space reference direction. Both "from_entity" and "to_entity" must be "ee". Requires either "axis" or "plane".
  - "gripper_aperture": Scalar gripper opening. Both entities must be "gripper_l" and "gripper_r".

Optional component selectors (pick at most ONE of axis / plane / ee_vector):
  - "axis" [x,y,z]: For positional pairs, signed 1-D projection onto this direction. For orientation pairs, signed cosine of the angle between the body vector and this direction.
  - "plane" [nx,ny,nz]: For positional pairs, magnitude of the in-plane component (perpendicular to the normal). For orientation pairs, magnitude of the body-vector projection in that plane.
  - "ee_vector" [x,y,z]: Only for orientation pairs. Selects which body-frame direction of the end-effector to track (defaults to [0,0,1]).
Set both "axis" and "plane" to null when the full 3-D distance is the right signal.

LAMBDA CONDITIONS
Each pre_condition / post_condition is expressed as a Python lambda string with the signature:
  lambda ee, keypoints, ee_R: <scalar expression>
where:
  - "ee" is a numpy array of shape (3,) — the end-effector XYZ position.
  - "keypoints" is a dict mapping entity IDs (int or "ee", "gripper_l", "gripper_r") to numpy arrays of shape (3,) with their 3-D centroid positions.
  - "ee_R" is the world-from-EE rotation matrix as a numpy array of shape (3, 3). "ee_R[:, 2]" is the gripper's body z-axis ("approach direction") in world coordinates.

The condition is SATISFIED when the returned scalar is <= 0. The lambda runs in a restricted sandbox where only the "np" module is available (no Python built-ins like max/min/abs/sum — use np.maximum, np.minimum, np.abs, np.sum). The lambda must return a scalar.

You may optionally emit "path_constraints" per sub-trajectory using the same lambda format and an extra "pairs_affected" list (labels of pairs whose guidance weight increases when the constraint is violated). Path constraints are optional in this strategy.

OUTPUT FORMAT
Return a JSON object with exactly one top-level key "subtrajectories" — a list of K objects in execution order. Each object has:
  - "subtraj_idx": integer 0..K-1.
  - "label": a short human-readable name (e.g. "approach", "lift").
  - "reasoning": 1-2 sentences describing the goal of this phase and why these pairs/conditions capture it.
  - "pre_condition": {"label": str, "description": str, "expression": str, "reasoning": str?}
  - "post_condition": {"label": str, "description": str, "expression": str, "reasoning": str?}
  - "pairs": list of pair objects with the same fields as the legacy schema (from_entity, to_entity, label, distance_type, axis, plane, ee_vector).
  - "path_constraints": optional list (may be empty) with the same fields as the legacy path_constraints schema.
